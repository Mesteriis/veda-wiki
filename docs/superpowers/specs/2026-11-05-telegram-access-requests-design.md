# Telegram-уведомления и запросы доступа к API/MCP — проект

Дата: 2026-11-05. Решения владельца:

- Интеграция с Telegram-ботом — **только уведомления**, отдельной страницы нет,
  настраивается в «Настройках».
- Уведомлять о: **запросах доступа**, **ошибках синхронизации GitHub**,
  **скором окончании срока ключей**.
- В публичном режиме — кнопка **«Запросить доступ к API/MCP»**: форма с выбором
  разделов (только публичные источники), ником в Telegram и комментарием;
  владелец получает уведомление.
- Запросы сохраняются: список в «Настройках», кнопки **«Выдать ключ»** и
  **«Отклонить»**; ключ человеку владелец передаёт сам.
- У пользователей в профиле — **Telegram ID**. Получатели уведомлений —
  **администраторы**, у которых он указан.
- Защита формы — **лимиты без капчи**, без внешних сервисов.

## Проверенные факты (2026-11-05)

- LXC161 достаёт `https://api.telegram.org` напрямую (HTTP 302 на корень).
- nginx-ui (CT112) проксирует `veda.sh-inc.dev` на `10.34.10.102:18443` и **не
  передаёт** адрес клиента (`X-Real-IP`/`X-Forwarded-For` не выставлены): для VEDA
  все запросы приходят с `10.34.10.7`. Лимит «по адресу» без доработки прокси не
  работает.
- Основное хранилище отклоняет неизвестные категории записей («unknown SQLite
  record category»): новые коллекции в нём сломали бы откат на прежний бинарник.

## Хранение — отдельно от основного хранилища

Новый файл `<data>/notify.sqlite` (0600, свой пакет, свои миграции), как
`knowledge.sqlite`: запросы доступа, Telegram ID пользователей, состояние
уведомлений (что уже отправлено). Токен бота — отдельный приватный файл
`<data>/telegram-bot.token` (0600), в ответах API никогда не возвращается.
Основное хранилище и его формат **не меняются**, откат на прежний бинарник
безопасен: он просто не знает о новых файлах.

## Telegram

- Пакет `internal/notify`: клиент Bot API (только `getMe` и `sendMessage`, без
  webhook и опроса — бот ничего не принимает), очередь отправки с повторами и
  дедупликацией. Токен и тексты сообщений с данными посетителей в журнал не
  пишутся.
- Получатели: администраторы с Telegram ID. Бот может написать человеку только
  после того, как тот нажал у бота «Start» — это написано рядом с полем.
- Сообщения по-русски, без Markdown-разметки (данные посетителя не должны
  превращаться в ссылки или форматирование):
  - запрос доступа: ник, разделы и комментарий (каждая строка комментария с
    отметкой «│», невидимые и управляющие символы отклоняются формой);
  - форма упёрлась в лимит — не чаще раза в сутки;
  - ошибка синхронизации: источник и код ошибки — один раз при переходе в ошибку
    и один раз при восстановлении;
  - срок ключа: за 24 часа до окончания, один раз на ключ.

## Публичная форма

- Кнопка в подвале боковой панели гостя, над «Войти»; на телефоне — в меню.
- Поля: разделы (флажки только публичных источников), ник в Telegram
  (`@` + 5–32 символа `[A-Za-z0-9_]`), комментарий до 1000 символов, скрытое
  поле-ловушка.
- `POST /api/public/access-requests` — **единственная запись, доступная
  анонимному посетителю**; только с того же origin, тело до 4 КБ, на всех
  слушателях, включая публичный. Это осознанное исключение из правила «запись из
  браузера запрещена»: запись касается только очереди запросов, не статей.
- Лимиты: 3 запроса в час с одного адреса, 20 в сутки всего, не больше 100
  ожидающих; при превышении — 429 и вежливый текст. Адрес клиента берётся из
  `X-Real-IP` **только** если запрос пришёл с адреса из нового флага
  `--trusted-proxy` (для прода — `10.34.10.7`); иначе — адрес соединения. Адрес
  в хранилище не записывается.
- Изменение на CT112: в сайт `veda.sh-inc.dev` добавить
  `proxy_set_header X-Real-IP $remote_addr;` (с `nginx -t` и откатом).
  **Порядок важен:** сначала nginx, потом флаг `--trusted-proxy 10.34.10.7`.
  Иначе nginx пропустит заголовок посетителя как есть, и любой сможет выдать
  себя за другой адрес. Флаг добавляется только в юнит нового бинарника: старый
  бинарник с ним не запустится (неизвестный флаг).
- При выдаче ключа разделы проверяются заново: если раздел стал приватным, ключ
  не выдаётся (409).
- При первом запуске о каждой уже сломанной синхронизации придёт одно
  сообщение; отметки «отправлено» ведутся и при выключенном событии.

## Настройки

На странице «Настройки» (управление доступом) две новые вкладки:

- **«Запросы доступа»**: ожидающие и обработанные; «Выдать ключ» создаёт ключ
  чтения на запрошенные разделы (срок по умолчанию 90 дней, можно изменить),
  показывает его один раз существующим окном выдачи ключа и помечает запрос
  выданным; «Отклонить» помечает отклонённым. Посетителю ничего автоматически не
  отправляется.
- **«Telegram»**: токен бота (вводится, проверяется `getMe`, дальше показывается
  только имя бота и «настроен»), кнопка «Отправить пробное», переключатели трёх
  видов уведомлений.

Профиль пользователя: поле «Telegram ID» (число) с подсказкой, как его узнать, и
пометкой, что уведомления приходят только администраторам.

## Не цели

- Приём сообщений ботом, команды бота, ответы посетителю через бота.
- Автоматическая выдача ключей.
- Капча и внешние сервисы защиты.

## Проверки

Go: хранилище `notify.sqlite`; клиент Telegram против фейкового сервера; очередь и
дедупликация; публичная форма — валидация, ловушка, лимиты, `--trusted-proxy`,
только публичные разделы, origin; выдача ключа по запросу; события GitHub и
сроков ключей. Фронтенд: форма гостя, вкладки, профиль. Ручная проверка после
развёртывания: пробное сообщение и реальный запрос с телефона.
