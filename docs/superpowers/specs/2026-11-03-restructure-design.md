# Перестройка VEDA: пакеты Go, TypeScript, MCP-адаптер на Go

Дата: 2026-11-03. Статус: черновик на утверждение владельцем.

## Зачем

Код VEDA должно быть не стыдно показать. Сейчас:

- весь бэкенд (около 11,5 тыс. строк кода и 17,5 тыс. строк тестов) лежит
  одним пакетом `main` в `server/`: 60 файлов кода и 85 файлов тестов вперемешку;
- почти вся логика — это около 100 методов одной структуры `Store` в 20 файлах,
  которые напрямую читают и меняют общую `Database` под одной блокировкой;
- есть файлы на 700–1100 строк (`sync.go`, `sync_test.go`, `api.go`, `store.go`,
  `import.go`), `web/src/styles.css` занимает 2476 строк;
- фронтенд написан на JavaScript без типов, запросы к серверу разбросаны по
  компонентам;
- MCP-адаптер — отдельный Python-файл на 412 строк, где перемешаны HTTP-клиент,
  описания инструментов и обработчики; на сервере ради него держится отдельное
  Python-окружение.

Владелец сформулировал главный критерий так: не должно быть файлов на тысячу
строк, а код должен быть разнесён по настоящим пакетам с понятными границами.
Простое разрезание файлов внутри пакета `main` не подходит.

## Цели

1. Бэкенд разнесён по пакетам Go с явными границами и направлением зависимостей.
2. Фронтенд переведён на TypeScript в строгом режиме и разложен по разделам.
3. MCP-адаптер переписан на Go и встроен в тот же бинарник как подкоманда.
4. Ни один исходный файл, включая тесты и CSS, не длиннее 500 строк; правило
   проверяется автоматически.
5. Линтеры и проверка типов не дают структуре расползтись обратно.

## Не цели

- Новые возможности и исправления поведения. Пункты 6–10 из плана работ
  (ревизии отдельными записями, картинки по ревизиям, хранение и индексы,
  модель перевода, параллельная синхронизация и пароли) — отдельные проекты
  после этого.
- Смена фреймворков: остаются Go, React и Vite.
- Настройка CI. Владелец отложил её. Существующий workflow обновляется только
  под новые пути, чтобы не сломаться.

## Анти-цели: провал, даже если «всё работает»

- Меняется наблюдаемое поведение: маршруты и формы JSON в REST API, коды
  ответов, флаги и подкоманды CLI, имена и описания MCP-инструментов, формат
  `state.json` и записей SQLite, права файлов, тексты интерфейса.
- Развёрнутый LXC161 не может обновиться без миграции данных или теряет откат
  на предыдущий бинарник.
- Остаются «переходные» пакеты вроде `legacy`, `common`, `util` или один пакет,
  в который просто переехал прежний `main`.
- Тесты ослаблены или удалены, чтобы перенос «прошёл».
- Пакеты обходят границы: лезут в данные других областей мимо их API.

## Ограничения

- Каждый коммит собирается и проходит `make test`. Внешние проверки
  (`scripts/smoke*.py`, `scripts/smoke_ui.py`, MCP smoke на официальном Python
  SDK) проходят в конце каждой фазы.
- Формат хранилища на диске не меняется: новый бинарник читает текущую базу
  LXC161, а предыдущий бинарник читает базу после нового.
- Правила `AGENTS.md`: слушатели по умолчанию на loopback, проверку Host не
  отключать, публичный слушатель игнорирует токены владельца, запись из
  браузера запрещена, секреты не попадают в ответы, логи и Git.
- Зависимости только закреплённых версий и только там, где без них не обойтись.

## Решения владельца

- Пакеты Go с настоящими границами, а не разрезанные файлы.
- Фронтенд на TypeScript.
- MCP-адаптер на Go, без отдельного Python-окружения на сервере.
- Перестраиваются все три части: бэкенд, фронтенд, адаптер.
- Порядок проектов: сначала эта перестройка, затем хранилище (6–8), перевод (9),
  мелочи от ревью (10).

## Устройство бэкенда

### Модуль и папки

Решение исполнителя (моё): `go.mod` переезжает в корень репозитория
(`module github.com/Mesteriis/veda-wiki`), папка `server/` исчезает. Это обычная
раскладка Go-проекта, и пути в Makefile, CI и скриптах обновляются вместе с ней.

Целевая раскладка (имена пакетов — моё решение, исполнитель может уточнить, если
граница окажется другой):

```
cmd/veda/                 точка входа: разбор подкоманд, вызов internal/app
internal/app/             сборка приложения: флаги, слушатели, воркеры, остановка
internal/domain/          типы Source, Article, Revision, Database и др.,
                          ошибки, проверки идентификаторов и путей,
                          чистые правила переходов состояния (без ввода-вывода)
internal/store/           Store: блокировка, транзакции View/Update, клон,
                          фиксация; бэкенды JSON и SQLite, миграции, фикстуры
internal/auth/            ключи доступа, пользователи и команды, пароли,
                          сессии браузера, лимит попыток
internal/github/          клиент GitHub API (без логики синхронизации)
internal/syncer/          фоновая синхронизация, очередь записи, публикация,
                          зеркала и согласование источников
internal/importer/        veda.yaml, импорт из локального репозитория,
                          сравнение, удаление импортированного источника
internal/transfer/        копирование, связанные графы, переносы, план переноса
internal/translation/     очередь и проверка переводов, локальный воркер
internal/search/          лексический поиск
internal/render/          Markdown, ссылки между источниками, оглавление, граф
internal/agentctx/        контекст AGENTS.md и предложения изменений
internal/httpapi/         HTTP-обработчики по разделам, проверка ролей
internal/mcp/             MCP-адаптер: клиент REST/сокета, инструменты
internal/webui/           встроенный собранный фронтенд (embed)
```

### Главный паттерн: функциональное ядро, оболочка с вводом-выводом

Сейчас бизнес-правила и фиксация данных перемешаны в методах `Store`. Новое
правило:

- `domain` хранит модель и **чистые функции** переходов над `*Database`:
  например, постановка записи в очередь, согласование переносов, правила
  публичности. Там нет блокировок, файлов, сети и времени из системных часов
  (время передаётся параметром).
- `store` отвечает только за целостность и долговечность: одна блокировка,
  `View(func(*domain.Database) error)` для чтения и
  `Update(func(*store.Tx) error)` для изменений. `Tx` даёт изменяемый клон и
  позволяет указать, что изменилось, чтобы SQLite записал только нужные записи
  (сейчас это `commitWithArticle` и `commitConnections`). Ошибка внутри `Update`
  ничего не фиксирует.
- Пакеты областей (`auth`, `syncer`, `importer`, `transfer`, `translation`,
  `agentctx`) описывают операции как функции или сервисы поверх `store`,
  используя правила из `domain`. Сеть и файлы — только в них, `github`,
  `importer` и `httpapi`.
- `httpapi` и `mcp` — адаптеры: разбирают вход, проверяют роль, вызывают
  операции области и сериализуют результат. Своей бизнес-логики в них нет.

Направление зависимостей: `cmd → app → httpapi/mcp → области → store → domain`.
`github` и `render` — листья. Циклы запрещены, и Go их всё равно не пропустит.
Область не импортирует другую область, кроме явно описанных случаев: `syncer`
использует `importer` для применения пакета импорта, `transfer` использует
правила очереди из `domain`. Общая логика, нужная двум областям, переезжает
в `domain`.

**Владение данными (моё решение).** У каждой коллекции `Database` один
пакет-владелец, только он её меняет:

| Коллекция | Владелец |
|---|---|
| `Sources`, `Articles` | `domain` (правила статей и источников) |
| `Outbox`, `Connections`, `Accounts`, `SourceMirrors` | `syncer` (через `domain`-правила очереди) |
| `Moves` | `transfer` |
| `AccessKeys`, `Users`, `Teams` | `auth` |

Остальные пакеты читают их через функции чтения в `domain` или API владельца, а
меняют только через API владельца. Перекрёстные правила, которые нужны при
записи статьи (поставить в очередь, согласовать переносы, проверить
публичность), — чистые функции `domain`, их вызывает операция записи. Это
проверяется ревью и тестом-архитектором: скрипт ищет присваивания в чужие
коллекции вне пакета-владельца.

Состояние в памяти, которое сейчас лежит в `Store`, переезжает к хозяевам:
`observed` и `withheld` (наблюдения импорта) — в `syncer`/`importer`, мьютекс
паролей — в `auth`. В `store` остаются только блокировка данных и фиксация.

Ограниченный просмотр для читателя с ключом (`scopedView`) становится функцией
`store`, которая строит снимок только из разрешённых источников. Обработчики
получают уже ограниченное хранилище, как сейчас.

### Тесты

- Модульные тесты переезжают в пакеты вместе с кодом и проверяют их API. Если
  тест держится за внутренности другой области, это признак неверной границы:
  исправляется граница или тест переписывается через API, но проверяемое
  свойство сохраняется.
- Общие тестовые помощники уходят в отдельные пакеты: фальшивый GitHub —
  `internal/github/githubtest`, сборка хранилища с данными —
  `internal/store/storetest`.
- Сценарии через несколько областей (синхронизация с переносами, SQLite после
  перезапуска, MCP-маршрутизация агентов) — в `internal/app` или
  `test/integration`, через публичные конструкторы.
- Число и смысл проверок не уменьшаются. В конце перестройки — таблица
  соответствия: каждый старый тест и куда переехало его свойство.
- Фикстуры старых форматов (v7–v13) и восстановления остаются и проходят.

## MCP-адаптер на Go

- Подкоманда `veda mcp` на официальном Go SDK
  (`github.com/modelcontextprotocol/go-sdk`, закреплённая версия, сейчас v1.8.0).
- Те же флаги (`--url`, `--key-file`, `--reader-key-file`,
  `--reader-key-preamble`, `--reader-socket`, `--allow-remote-reader-https`),
  те же проверки (loopback или явно разрешённый HTTPS для читателя, приватный
  сокет и его каталог, файл ключа с правами владельца, запрет перенаправлений
  и прокси, лимит ответа 24 МБ, таймауты по маршрутам).
- Те же инструменты, описания, схемы, инструкции сервера, набор только для
  чтения и тексты отказов с HTTP-кодом. Описания инструментов совпадают
  с Python-версией дословно, кроме технически необходимых отличий.
- Клиентский помощник `mcp/keyed_stdio_launcher.py` становится подкомандой
  `veda mcp-relay` (моё решение): он работает на машине агента, поэтому агентам
  понадобится бинарник `veda` для их ОС.
- Python-адаптер удаляется только после того, как существующие smoke-проверки
  на официальном Python SDK (`scripts/smoke.py`, `smoke_mcp_https.py`, MCP-тесты
  Go в CI) проходят против `veda mcp`. Python остаётся в репозитории только как
  инструмент внешних проверок.
- Где работает адаптер: как сейчас, на LXC161 через ssh (`veda mcp
  --reader-socket …`), то есть `veda mcp` достаточно для Linux. На машине агента
  работает только `veda mcp-relay`, поэтому релиз дополнительно собирает
  `darwin/arm64` (моё решение; сейчас все четыре клиента на Mac владельца).
- Python-адаптер удаляется из репозитория и архива релиза в фазе 2. На LXC161
  файл `/opt/veda-next/mcp/server.py` при этом не удаляется: установщики меняют
  только конкретные файлы, поэтому откат сохраняется до подтверждения
  переключения.
- Переключение LXC161 и конфигураций четырёх клиентов — отдельный шаг
  развёртывания после слияния: лаунчеры начинают вызывать
  `/opt/veda-next/veda mcp …`, а старый `server.py` остаётся откатом до
  подтверждения.

## Фронтенд на TypeScript

- TypeScript в строгом режиме (`strict`, без неявного `any`), сборка Vite
  падает на ошибках типов (`tsc --noEmit` в `make test`).
- Раскладка (моё решение):

```
web/src/
  main.tsx, App.tsx       вход и маршрутизация по параметрам адреса
  api/                    типизированный клиент: состояние, сессии, доступ, GitHub;
                          типы ответов API в одном месте
  hooks/                  опрос состояния, сессия, горячие клавиши
  components/             оболочка, боковая панель, шапка, диалог, иконка
  features/reading/       статья, оглавление, предупреждения
  features/catalog/       каталог, дерево, результаты поиска
  features/home/          главная, карточки, активность
  features/graph/         граф связей
  features/recent/        недавние
  features/access/        пользователи, команды, ключи
  features/github/        подключения, аккаунты, зеркала
  features/session/       вход, пароль, вход по ссылке
  styles/                 tokens.css (цвета, отступы, шрифты), base.css
```

- CSS разносится по разделам рядом с компонентами, общие значения — переменные
  в `tokens.css`. Внешний вид не меняется (моё решение о проверке): снимки
  экранов до и после на ширинах 1672, 390 и 320 для гостевой главной, каталога,
  статьи, графа, недавних, входа, настроек доступа и страницы GitHub (последние
  два — на синтетическом администраторе из браузерного smoke). Сравнение
  попиксельное с порогом 0,1% отличающихся пикселей на экран; всё, что выше,
  разбирается вручную и либо исправляется, либо явно принимается владельцем.
  Порядок каскада сохраняется: стили переносятся по разделам в прежнем порядке
  подключения, реорганизация правил — только когда снимки совпадают.
- Чистая логика (`tree`, `catalog`, `recent`, `statePoll`, `link-login`,
  `githubErrors`, `sourceWarnings`) переходит на TypeScript со своими тестами.
  Средство запуска тестов — решение исполнителя (например, Vitest
  закреплённой версии).
- Линтер ESLint с правилами для TypeScript и React hooks.

## Защита от расползания

- Скрипт проверки размера файлов: не больше 500 строк на исходный файл
  (`.go`, `.ts`, `.tsx`, `.css`, `.py`), исключения только для сгенерированных
  файлов и lock-файлов, список исключений в самом скрипте. Запускается
  в `make test` и включается по мере готовности (моё решение): для Go — в конце
  фазы 1, для фронтенда — в конце фазы 3, для Python-скриптов проверок — сразу.
- Go: `gofmt`, `go vet` и `staticcheck` (закреплённая версия) в `make test`.
- Фронтенд: `tsc --noEmit` и ESLint в `make test`.

## Порядок работы

Три фазы, каждая — отдельный PR в `main`, каждый коммит зелёный:

1. **Бэкенд.** Перенос `go.mod`, затем листья (`domain`, `render`, `search`,
   `github`), затем `store` с транзакциями, затем области по одной, затем
   `httpapi`, `app` и `cmd/veda`. Прежний пакет `main` исчезает целиком.
2. **MCP-адаптер на Go.** `veda mcp` и `veda mcp-relay`; доказательство
   совместимости — Python smoke-тесты; затем удаление Python-адаптера.
3. **Фронтенд на TypeScript.** Типы и клиент API, затем разделы по одному,
   затем CSS; скриншоты до и после.

После каждой фазы обновляются README, `AGENTS.md`, `docs/` и пути в Makefile,
CI и скриптах.

Развёртывание на LXC161 — после всех трёх фаз, обычным порядком: PBS-снимок,
защищённый установщик с откатом, затем переключение лаунчеров MCP.

## Оставлено исполнителю

- Точные имена пакетов и файлов внутри описанных границ.
- Разбиение `httpapi` на файлы и способ регистрации маршрутов (сохраняя
  проверку роли в самой маршрутизации, как сейчас в `routeAPI`).
- Формы сервисов областей (функции или структуры с зависимостями).
- Средство запуска фронтенд-тестов и конфигурация линтеров.
- Порядок переноса областей внутри фазы 1.
