# Страница «API и MCP» — проект

Дата: 2026-11-05. Решение владельца: в разделе «API и MCP» нужны все четыре части —
подключение агентов, список инструментов MCP, справка по REST API и активность
агентов. Сейчас пункт меню открывает диалог с одним абзацем текста.

## Что видит пользователь

Пункт меню «API и MCP» открывает полноценную страницу `/?api=1` (как «GitHub» и
«Настройки»), доступную владельцу и вошедшему администратору; гость её не видит.
Четыре вкладки:

1. **Подключение агентов.** Выбор клиента (Claude Code, Codex, OpenCode, Hermes) и
   способа доступа; готовая команда с кнопкой «Скопировать».
   - *Чтение по ключу через HTTPS* — работает с любой машины, где есть бинарник
     `veda`: `veda mcp --url <адрес этого сайта> --reader-key-file <файл> --allow-remote-reader-https`.
     Адрес подставляется из текущего origin. Ссылка «Создать ключ» ведёт в
     «Настройки → Ключи доступа».
   - *Редактор через SSH* — ключ владельца остаётся на сервере:
     `ssh <хост> '<путь>/veda mcp --editor --url http://127.0.0.1:<порт> --key-file <файл>'`.
     Хост, путь, порт и файл ключа сервер не знает о себе надёжно — поля с
     подсказками, введённые значения запоминаются в браузере (localStorage, не
     сервер). Ключ владельца в интерфейсе никогда не показывается.
   - Пояснение: какой режим что разрешает, перезапуск клиента после смены.
2. **Инструменты MCP.** Таблица из сервера: имя, описание, доступность в режимах
   «чтение», «редактор», «владелец». Источник — та же таблица `internal/mcp.Tools`,
   что и у сервера MCP, через `GET /api/v1/mcp/tools`, поэтому список не расходится
   с реальностью.
3. **REST API.** Основные маршруты чтения и записи (статьи, поиск, контекст,
   источники, GitHub, ключи) с методом, назначением, требуемой ролью и примером
   `curl` с текущим origin и плейсхолдером ключа. Список статический в интерфейсе,
   ссылка на полную `docs/api.md` в репозитории.
4. **Активность.**
   - *Клиенты MCP*: когда каждый режим (чтение — общий для ключей и сокета,
     редактор, владелец) последний раз обращался к серверу. `veda mcp`
     помечает свои запросы заголовком `X-Veda-Client: mcp/<режим>`; сервер хранит
     время последнего обращения в памяти (сбрасывается при перезапуске — так и
     подписано). Отсюда же статус «MCP» в боковой панели (только владельцу и администратору) вместо
     «Неизвестно»: «активен N мин назад» / «нет обращений с запуска».
   - *Последние изменения через MCP*: ревизия статьи получает необязательное поле
     `via` («mcp-editor», «mcp-owner», «rest»; у импортированных ревизий поля нет); страница показывает 20
     последних ревизий, записанных через MCP, со ссылками на статьи. Старые
     ревизии без поля показываются как «неизвестно». Поле `omitempty`: формат
     хранилища не меняется; при сверке заголовка статьи с ревизией `via` не
     сравнивается, поэтому откат и повторное обновление безопасны.
   - *Ключи доступа*: список ключей с источниками и сроком (уже есть
     `GET /api/v1/access-keys`) и ссылка на управление в «Настройках».

## Сервер

- `GET /api/v1/mcp/tools` — владелец и администратор; ответ из `mcp.Tools`
  (`name`, `description`, `modes`). Без схем ввода.
- `GET /api/v1/mcp/activity` — владелец и администратор: последние обращения по
  режимам и 20 последних ревизий с `via` на `mcp-*`.
- Middleware в `httpapi` читает `X-Veda-Client` только как метку (не авторизация);
  неизвестные значения отбрасываются. Режим определяется по фактической
  авторизации, а метка лишь отличает MCP от прочих клиентов.
- `Revision.Via` выставляется в обработчике записи статьи по той же метке.
- Документация: `docs/api.md`, `docs/agent-workflow.md`.

## Не цели

- Создание ключей и пользователей на этой странице (остаётся в «Настройках»).
- Интерактивный «попробовать запрос» к REST.
- Постоянное хранение журнала активности клиентов.

## Проверки

Go-тесты на оба маршрута и на `via`; фронтенд-тесты на генерацию команд и вкладки;
проверка в браузере на синтетическом предпросмотре; `make lint`, `make test`.
